# MapApp — карта с локальной базой данных

Учебное приложение на **Expo / React Native** (Expo Router, TypeScript): интерактивная карта,
маркеры с фотографиями и локальное хранилище на **SQLite**. Все данные сохраняются на
устройстве и остаются после перезапуска приложения.

Задание 2: добавление локальной базы данных SQLite и управление доступом к ней через
React Context.

---

## Возможности

- карта на `react-native-maps` (Android/iOS) и Leaflet (web);
- добавление маркера долгим нажатием (на телефоне) или двойным кликом (в браузере);
- список маркеров с датой создания и количеством изображений;
- экран маркера: координаты, дата, галерея изображений;
- добавление изображений из галереи (копируются в постоянное хранилище приложения);
- удаление маркеров и изображений с подтверждением и удалением файлов;
- хранение всего состояния в SQLite: `markers` + `marker_images` (`ON DELETE CASCADE`);
- обработка ошибок на всех уровнях, повторная инициализация базы, логирование в dev-режиме.

## Установка и запуск

Требования: Node.js 20+, npm. Для Android — приложение **Expo Go** (SDK 58).

```bash
npm install
npx expo start          # dev-сервер, QR-код для Expo Go
npx expo start --android
npx expo start --ios
npx expo start --web    # карта на Leaflet
```

Проверки:

```bash
npm run typecheck       # tsc --noEmit
npm run lint            # eslint (eslint-config-expo)
npx expo export --platform web   # проверка веб-сборки
```

> На веб-платформе `expo-sqlite` использует WebAssembly, поэтому в `metro.config.js`
> добавлены поддержка `.wasm` и заголовки `Cross-Origin-Embedder-Policy` /
> `Cross-Origin-Opener-Policy` (нужны для `SharedArrayBuffer`). Если публикуете
> веб-сборку, эти заголовки нужно настроить и на хостинге.

## Схема базы данных

Файл базы: `markers.db` (каталог `SQLite` песочницы приложения).
Схема создаётся в `src/database/schema.ts` ровно в том виде, который требуется в задании.

```sql
CREATE TABLE markers (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    latitude REAL NOT NULL,
    longitude REAL NOT NULL,
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE marker_images (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    marker_id INTEGER NOT NULL,
    uri TEXT NOT NULL,
    created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
    FOREIGN KEY (marker_id) REFERENCES markers (id) ON DELETE CASCADE
);

CREATE INDEX idx_marker_images_marker_id ON marker_images (marker_id);
```

Связь: **один маркер → много изображений**. Удаление маркера каскадно удаляет его
изображения (`ON DELETE CASCADE`), а индекс по `marker_id` ускоряет выборку галереи.

### Соединение и версионирование

При открытии базы (`initializeDatabase()`):

1. `PRAGMA foreign_keys = ON` — внешние ключи в SQLite выключены по умолчанию и
   задаются для каждого соединения (обязательно вне транзакции);
2. `PRAGMA journal_mode = WAL` — быстрее запись, меньше блокировок (на web пропускается);
3. миграции по `PRAGMA user_version`: каждая следующая версия применяется в собственной
   транзакции, затем выставляется `user_version`. Если база новее приложения — выбрасывается
   понятная ошибка.

Добавление новой миграции:

```ts
// schema.ts
export const DATABASE_VERSION = 2;      // увеличить
const MIGRATIONS = {
  1: ...,
  2: async (db) => { await db.execAsync('ALTER TABLE markers ADD COLUMN title TEXT;'); },
};
```

### Операции (`src/database/operations.ts`)

| Функция | Назначение |
| --- | --- |
| `insertMarker(db, lat, lng)` | создание маркера, возвращает `id` (с валидацией координат) |
| `selectMarkers(db)` | все маркеры вместе с изображениями за **2 запроса** (без N+1) |
| `selectMarkerById(db, id)` | один маркер с галереей |
| `deleteMarker(db, id)` | удаление в транзакции, возвращает URI файлов для очистки |
| `selectMarkerImages(db, markerId)` | изображения маркера |
| `insertMarkerImage(db, markerId, uri)` | добавление изображения (проверка существования маркера) |
| `deleteMarkerImage(db, id)` | удаление записи, возвращает URI файла |
| `selectStats(db)` | количество строк — для диагностических логов |

Слой не зависит от React: функции принимают `SQLiteDatabase` и возвращают доменные
объекты с camelCase-полями (`marker_id` → `markerId`, `created_at` → `createdAt`).

## Контекст базы данных (`src/contexts/DatabaseContext.tsx`)

`DatabaseProvider` — единственный владелец соединения. Он открывает базу при монтировании,
закрывает её при размонтировании (`closeAsync`, с защитой от гонки при быстром размонтировании),
держит кэш маркеров в состоянии и оборачивает все операции в обработку ошибок.

```ts
interface DatabaseContextType {
  // обязательные операции из задания
  addMarker: (latitude: number, longitude: number) => Promise<number>;
  deleteMarker: (id: number) => Promise<void>;
  getMarkers: () => Promise<Marker[]>;
  addImage: (markerId: number, uri: string) => Promise<void>;
  deleteImage: (id: number) => Promise<void>;
  getMarkerImages: (markerId: number) => Promise<MarkerImage[]>;

  // статусы
  isLoading: boolean;
  error: Error | null;

  // дополнительные удобства для UI
  markers: Marker[];
  isReady: boolean;
  getMarker: (id: number) => Marker | null;
  retryInitialization: () => void;
  clearError: () => void;
}
```

Хук `useDatabase()` бросает ошибку, если провайдер не подключён, — это сразу заметно при
разработке. После каждой мутации кэш маркеров обновляется одним запросом, поэтому все
экраны видны согласованно.

## Обработка ошибок

| Уровень | Что сделано |
| --- | --- |
| Инициализация БД | ошибка открытия/миграции попадает в `error`, на карте появляется оверлей с кнопками «Повторить» и «Список маркеров» |
| Транзакции | удаление маркера и связанных изображений выполняется в `withTransactionAsync`; при сбое изменения откатываются, а файлы не удаляются |
| Нарушения ограничений | перед вставкой изображения проверяется существование маркера, иначе — понятное сообщение вместо `FOREIGN KEY constraint failed`; координаты валидируются до записи |
| Подключение | все операции требуют открытое соединение; если базы нет — `«База данных ещё не готова…»`, а не падение |
| UI | ошибки не скрывают данные: список показывает `ErrorBanner` с «Повторить»/«Скрыть», карта — оверлей; неудачные операции откатываются, интерфейс остаётся рабочим |
| Восстановление | `retryInitialization()` переоткрывает базу и перечитывает данные без перезапуска приложения |
| Логирование | `utils/logger.ts` пишет операции, миграции и ошибки в консоль только в `__DEV__`, ошибки — всегда |

Порядок работы с файлами подчёркивает атомарность: сначала фиксируется транзакция в базе,
и только затем удаляются файлы изображений (файловая система не умеет откатываться).

## Изображения

- `expo-image-picker` отдаёт URI во временном кеше — система может его очистить;
- поэтому `persistPickedImage()` копирует файл в `documentDirectory/marker-images/` и
  возвращает постоянный путь, который и попадает в `marker_images.uri`;
- при удалении изображения или маркера файл удаляется, но только если он лежит внутри
  папки приложения (чужие пути и `data:`-URI не трогаются);
- на web файловая система недоступна, поэтому изображение конвертируется в `data:`-URI и
  хранится прямо в базе.

## Исправление бага «метки не убираются»

До этого задания удаление работало только в памяти, а карта на Android иногда оставляла
«фантомную» метку. Что изменено:

1. **Данные — источник истины.** Метки на карте строятся из состояния контекста, а состояние
   обновляется после успешного `DELETE` в SQLite. Удалённого маркера в массиве больше нет.
2. **Стабильные идентификаторы.** У каждой метки задан `key={marker.id}` (числовой id из базы)
   и `identifier={String(marker.id)}` — react-native-maps корректно сопоставляет нативные метки.
3. **Обход бага react-native-maps на Android (Fabric).** Если количество меток уменьшилось,
   `MapView` пересоздаётся (`key`), а текущая область карты сохраняется в состоянии, поэтому
   пользователь не замечает «прыжка». Это задокументированный обходной путь для случаев,
   когда нативный слой не синхронизирует удаление метки.
4. **Веб.** Метки Leaflet пересоздаются при каждом изменении списка, а ошибка больше не
   заменяет контейнер карты (иначе после «Повторить» Leaflet терял DOM-узел).

## Дополнительно реализовано

- миграции схемы через `PRAGMA user_version` (готова точка расширения до v2);
- `PRAGMA foreign_keys = ON` + `ON DELETE CASCADE` и «страховочное» удаление изображений,
  если платформа не применила прагму (web);
- транзакции для операций с двумя таблицами;
- индекс `idx_marker_images_marker_id`;
- загрузка маркеров с изображениями за 2 SQL-запроса (без N+1);
- WAL-режим;
- строгая типизация доменных объектов и маппинг snake_case → camelCase в одном месте;
- логирование SQL-операций и статистики в dev-режиме;
- переподключение к базе без перезапуска приложения;
- очистка ресурсов: соединение закрывается при размонтировании, файлы удаляются вместе
  с записями;
- адаптивный UI: подтверждения через `Alert` на телефоне и `window.confirm` в вебе,
  состояния загрузки и баннеры ошибок, счётчик маркеров на кнопке списка.

## Почему без ORM

Выбран «чистый» `expo-sqlite`: для двух таблиц и шести операций ORM (Prisma/Drizzle)
добавляет генерацию кода, отдельный слой миграций и вес сборки, не давая выигрыша.
SQL в этом проекте короткий, параметризованный (`?`, без конкатенации пользовательских
данных) и полностью типизирован на границе слоя доступа к данным. Миграции при этом
реализованы штатным механизмом SQLite (`user_version`), а не сторонним инструментом.

Пакет `@types/sqlite3` из списка зависимостей задания относится к Node-драйверу
`sqlite3` и не нужен: типы для `expo-sqlite` поставляются вместе с библиотекой.
